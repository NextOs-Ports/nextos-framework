# NXExtract 1.2.2

Patch release. A stage that fails whole-set validation is no longer resumed and
re-rejected forever.

## Changes

- discards the stage and `state.json` when `validate_recipe_outputs(full=True)`
  raises, so the next run extracts from scratch instead of resuming data that is
  already known to be bad;
- logs `discarding staged data that failed validation (next run extracts from
  scratch)` before removing anything, so a support report shows why the next run
  re-extracted;
- leaves every other transactional path unchanged: staging, per-item validation,
  commit, rollback and the post-install data gate are untouched, and a *passing*
  stage is still resumed normally.

Extraction accepts each payload on its own as it is staged. Whole-set validation
runs afterwards and can reject a stage that no single item rejected — a missing
companion payload, an ABI mix, a split that landed without its base. Until now
that stage stayed on disk and the resume path picked it up on the next launch,
revalidated the identical bytes and raised the identical error. The field log
from Hitman GO 1.1.1 reads `resuming 1.2 GiB of already validated staged data`
followed by the same validation failure, on every retry, with no route out short
of deleting the workspace by hand. The port carried this as a local patch; it
belongs upstream so ports vendor a clean tree with no local patches.

Resuming a good stage saves a user gigabytes of re-extraction. Resuming a bad
one only reproduces the failure.

The Python core still supports Python 3.7 or newer. The bundled AArch64 UI is
unchanged and requires only GLIBC 2.17. No proprietary game data is included.
