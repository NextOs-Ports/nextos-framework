# NXExtract 1.2.20

NXExtract 1.2.20 hardens APK-COMPAT-01 (item 9 of the V3 audit): the cosmetic
identity of the owner-provided container may NEVER decide compatibility, and a
required member now carries an enforced runtime role. The setup screen pixels, the
separately pinned immutable UI, the terminal-result schema and the NXE####
format are unchanged. Runner and runtime-env are byte-identical to 1.2.19.

## Why

1.2.19 already banned container sha256/crc32/size as acceptance predicates, but
a recipe could still gate on the container SIGNATURE/certificate, the file
NAME, the exact versionCode, `source_validate`, a literal container
`source.patterns`, or signing material in `META-INF` — all of which are
identity, not compatibility.
A re-signed, renamed or versionCode-bumped build that is structurally identical
must stay compatible. Separately, `required_members` was a flat list with no way
to say a member is optional, variant-specific, or only a patch selector.

## What changed

- Container rules now refuse, in `validate`, `source_validate` and
  `output_validate`, the cosmetic identity keys:
  signature / signing certificate (NXA0004), file name (NXA0005) and exact
  versionCode (NXA0006). Those belong in `reference_build` (documentation).
- Final-output and hook-checkpoint checks aimed at the copied container obey
  the same ban; its destination is fixed and cannot inherit `{basename}`.
- `scan_static_suspects` additionally flags 40-hex SHA-1 signing-certificate
  fingerprints used by custom logic (NXA0054), skipping the 40-hex substrings
  of a 64-hex literal it already reports.
- `compatibility.required_members` accepts, in addition to plain member paths
  (each an implicit `core_required`), role-tagged objects
  `{member, role[, variant]}` with roles `core_required`, `optional`,
  `variant_required` and `patch_selector` (NXA0026..NXA0029). A member path is
  still structure, never a hash (NXA0027).
- The roles are enforced over the logical APK set (base plus splits, never the
  bundle wrapper): core is mandatory, optional never gates, variant gates only
  its resolved ABI, and a patch selector is authenticated by its internal
  SHA-256. Exactly one match selects a profile; absent or unknown bytes select
  the common generic/symbolic fallback.
- The resulting `org.nextos.nxextract.compatibility-result/1` document enters
  the plan fingerprint and hook checkpoint, is provided read-only through
  `NXEXTRACT_COMPATIBILITY_JSON`, and is persisted in the install marker with a
  separate digest. This prevents output from one profile/fallback being resumed
  for another input.
- Shared fixtures and real installs cover the new bans and roles, including
  renamed/re-signed containers, APK/APKM/APKS/XAPK and Terraria's documented
  `.4` versus internal `.49`. The named, fully synthetic
  `offtheroad-arm64-2-roles.json` fixture installs without `AVConfig.json`,
  requires AArch64 `libgame.so` and `libc++_shared.so` plus
  `assets/data_001.xpk`, accepts renamed/repackaged containers and rejects
  package, ABI, ELF and critical-data mismatches.

## Compatibility

Published ports keep their vendored engines; 1.2.19 stays a supported engine in
the registry. This correction happened before any 1.2.20 tag/release, so the
incomplete pre-release hash is not retained as a supported identity. Recipes
that never locked the container by identity need no change; a recipe carrying
those values as an acceptance predicate must remove the gate before adopting
1.2.20. The
canonical apkcompat module remains embedded verbatim (sync-gated byte identity)
into the engine, NXGenerator and NXRelease.
