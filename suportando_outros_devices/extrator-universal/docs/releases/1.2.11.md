# NXExtract 1.2.11

NXExtract 1.2.11 makes the mandatory setup UI **fail-open for the player and
fail-closed for QA**, and names the renderer failure instead of hiding it. The
approved graphical interface, the extraction order, the transaction boundary,
the SDL/direct-framebuffer drawing source, the goldens and all four GLIBC 2.17
release UI artifacts remain byte-for-byte unchanged. When a visible renderer
opens, nothing about the run changes.

## Headless fallback (P11.7)

Field case: on a CFW whose display stack cannot give the setup UI a renderer
(NXE7001 on muOS/RG35XX-H), the installation used to die even though the UI is
only a progress bar. Now, when the mandatory UI cannot open a visible renderer
— binary unavailable, failed start, exit before readiness, an unapproved proof
such as `visible=tty`, a proof published by an already-dead helper, or the
40-second readiness boundary — the engine logs the reason, terminates the
helper and **continues headless: the game still installs**.

Every readiness rule is still enforced exactly as before; the only change is
the consequence. Setting `NXEXTRACT_REQUIRE_VISIBLE_UI=1` restores the
historical fail-closed behaviour, which is what release/QA gates use to keep
proving the visible UI on hardware.

## Named renderer failures (P11.6)

The fallback log line carries the last line the UI itself wrote (for example
the exact `SDL_CreateWindow` error), so a field report names the cause without
a second round trip.

## Terminal result: `ui` object

`nxextract-result.json` gains a required `ui` member:

```json
"ui": {"mode": "visible" | "headless-fallback" | "disabled",
        "renderer": "sdl" | "fbdev" | null,
        "fallback_reason": "..." | null}
```

`visible` attests the approved renderer that opened; `headless-fallback`
records why the visual progress bar was skipped while the installation
completed; `disabled` covers runs where the UI was off or optional and absent.
The version-1 schema is extended with this member; every other member is
unchanged.
